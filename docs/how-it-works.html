Agent Orchestra: how it works

One chat with an orchestrator runs every project. It never holds project code: it writes short briefs, hands them to workers through orch, and accepts work only when a check it did not write passes.

The loop

  1. You ask for something in the hub chat. The orchestrator loads the project's state card, not its code.
  2. It splits the work, picks a worker per task, and writes a brief: goal, scope, verify command, pointers to files.
  3. orch dispatch starts a fresh worker in the repo with the contract and the brief.
  4. The worker ends with a fixed ### RESULT block. orch keeps that block and adds what it measured: exit code and files changed.
  5. orch verify checks the changes stay in scope and runs the verify command.
  6. Only the result and the verdict reach the chat. You get the outcome in a few lines.

Where the tokens are saved

  • The orchestrator's context holds state cards, briefs and capped results. Transcripts and code stay on disk.
  • Workers start empty and load no skills; their whole prompt is the contract plus one brief.
  • Skills load only when needed; five descriptions is the standing cost.
  • Fully specified tasks go to local Qwen, which costs nothing per token.
  • Handoff restarts the chat from a 40-line file once it grows long.

What makes the output reliable

  • Dispatch refuses a brief with no goal, no scope or no acceptance criteria.
  • A worker's claim is never the evidence. Changed files and the verify exit code are measured outside the worker.
  • Changes outside the declared scope reject the task.
  • No verify command means the task cannot be marked verified.
  • Two local failures escalate the task to a stronger worker.
